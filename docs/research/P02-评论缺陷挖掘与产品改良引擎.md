# P02 评论缺陷挖掘与产品改良引擎

评级：🎯 P0（痛点 4.2 / 难度 2.0） | 层级：L2 | 实施角色：算法
技术钩子：Embedding 微调、对比学习、难负例挖掘、聚类、LLM 归因与证据引用
目标客户：B2C 平台卖家、DTC 品牌、工贸一体企业
为什么推荐：全套项目我最推荐的入门算法项目。真实公开数据（Amazon Reviews 2023）、评测口径清晰、能做出干净的量化提升、业务价值直接。技术、数据、业务三样都占。

## 1. 业务场景

### 1.1 场景还原

星辰科技（深圳，35 人，年 GMV 8000 万，见 B1 §4.1）有一款卖了两年的 65W 氮化镓充电器，是店铺的现金牛，月销 3000 单。

2025 年 9 月，运营总监老王发现一个异常：这款产品的评分从 4.5 缓慢滑到 4.2，退货率从 3.8% 涨到 6.1%。

他让运营小张去看评论。小张花了两天，翻了最近 400 条评论，交上来一份 Excel，结论是：「客户反馈质量问题较多，建议联系供应商改善品控。」

这份结论毫无用处。 老王想知道的是：

到底是什么质量问题？外壳、插脚、发热、还是充电速度？

是所有批次都有，还是某个批次集中爆发？

是产品本身的问题，还是详情页描述与实物不符导致的预期落差？

美国站和德国站的抱怨是一样的吗？

竞品有没有同样的问题？

小张答不上来。不是他不努力，是人工看评论这件事本身有天花板：

| 限制 | 说明 |
|---|---|
| 看不完 | 这款产品累计 8000 条评论，全平台全 SKU 累计 40 万条 |
| 记不住 | 看到第 200 条时已经忘了第 30 条说了什么 |
| 归不了类 | "充电慢""半天充不满""要充 5 小时"是同一个问题，但人工容易当成三个 |
| 看不出分布 | 无法回答"这个问题占多大比例""是不是在变严重" |
| 语言障碍 | 德语、法语、日语评论直接跳过 |
| 无法关联 | 无法把评论问题关联到批次、供应商、时间 |

### 1.2 更糟的是：这不是一次性任务

老王的真实需求不是"分析这一款产品"，而是：

```text
450 个在售 SKU × 每天新增约 300 条评论 × 6 个站点 × 5 种语言
↓
需要一个持续运行的监控系统，而不是一次性的人工分析
```

而且要能触发行动：

| 发现的问题 | 应该通知谁 | 应该做什么 |
|---|---|---|
| 产品缺陷（外壳开裂） | 供应链 + 工厂 | 改模具、换材料、追溯批次 |
| 描述不符（尺寸偏小） | 运营 | 改 Listing 描述和图片 |
| 使用方法不清 | 运营 + 客服 | 加说明书、加 FAQ、改 A+ 页面 |
| 包装破损 | 供应链 + 物流 | 改包装、换物流商 |
| 物流延误 | 物流 | 换渠道 |
| 客户预期偏差 | 运营 | 调整营销话术 |

这张表是本项目的灵魂。 大多数"评论分析"项目只做到"分类出负面评论"，就结束了。真正有价值的是把问题路由到能解决它的人，并追踪整改效果。

### 1.3 这个痛点值多少钱

以星辰的规模测算（测算，非实测）：

| 收益项 | 测算逻辑 | 年化金额 |
|---|---|---|
| 降低退货率 | 找出 Top 3 缺陷并改良，退货率从 4% 降到 3%，GMV 8000 万 × 1% × (产品成本+物流+处理成本占比约 60%) | 约 48 万 |
| 提前发现批次问题 | 每年约 2 次批次性缺陷，提前 3 周发现可减少约 60% 受影响订单 | 约 30 万 |
| 减少差评导致的转化损失 | 评分从 4.2 回到 4.5，转化率提升约 5%（行业经验） | 约 100 万+（机会收益） |
| 节省人工分析 | 2 人 × 每月 3 天 × 12 月 | 约 6 万 |
| 合计 | 约 180 万 |  |

主动区分"实测"和"测算"，主动指出哪部分不确定——这个诚实度本身就是加分项。

## 3. 为什么这是一个 AI 问题

### 3.1 先排除不需要 AI 的方案

做项目前必须先问：能不能不用 AI？

| 备选方案 | 能不能解决 | 为什么不够 |
|---|---|---|
| 关键词规则（匹配"broken""slow"等） | ❌ | 表达方式无穷（"took forever to charge"没有 slow）；多语种规则要维护 5 套；无法发现未知问题 |
| 平台自带的评论分析 | ❌ | 只给情感极性和粗粒度标签，无法定位具体缺陷 |
| 直接把评论丢给大模型总结 | ⚠️ 部分 | 8000 条评论放不进上下文；每次结果不一致；无法给出量化分布；成本高 |
| 传统主题模型（LDA） | ❌ | 短文本 + 多语种上效果很差，这是行业资料里的常见错误建议 |

正确做法：多语种 Embedding → 聚类 → LLM 打标签。这也是本项目的核心链路。

### 3.2 为什么 Embedding 微调是关键

用通用 Embedding 模型直接聚类，会遇到一个致命问题：它按"话题"聚，不按"问题"聚。

```text
通用 Embedding 会把这两条聚在一起（都在讲充电速度）：
A: "Charges my phone in 30 minutes, super fast!"        ← 好评
B: "Takes forever to charge, waste of money"            ← 差评

而我们需要的是把这两条聚在一起（都是同一个缺陷）：
B: "Takes forever to charge, waste of money"
C: "充电速度比宣传的慢很多，5 小时才充满"                ← 中文，同一问题
```

通用模型的语义空间不是为"产品缺陷"这个任务设计的。

微调的目标：让"描述同一个缺陷的评论"在向量空间里靠近，无论语言和表达方式。

这就是对比学习的用武之地：

```text
正样本对：两条描述同一缺陷的评论（可跨语言）
负样本对：两条描述不同缺陷的评论
难负例：  话题相同但缺陷不同（如"充电快"vs"充电慢"）← 最关键
```

难负例挖掘是这个项目的技术核心。 简单负例（随机采样）模型很容易区分，学不到东西。真正让模型进步的是"看起来很像但其实不同"的样本对。

## 4. 目标流程

```text
【离线：模型构建】
公开评论数据集
↓
① 数据清洗与语言识别
↓
② 构建对比学习训练对（含难负例挖掘）
↓
③ Embedding 模型微调
↓
④ 在人工标注的金标准集上评测 ← ⭐ 必须独立标注
↓
⑤ 冻结模型，进入线上流程

【在线：持续运行】
新增评论（每日）
↓
① 预处理：清洗、语言识别、去重
↓
② 情感与相关性过滤：只保留可能含问题的评论
↓
③ Embedding 编码（用微调后的模型）
↓
④ 增量聚类：归入已知问题簇 or 形成新簇
↓
⑤ 新簇检测 → 触发 LLM 打标签
↓
⑥ LLM 归因：这个簇是什么问题？属于哪个类别？证据是哪几条？
↓
⑦ 关联分析：关联 SKU、批次、时间、站点、供应商
↓
⑧ 严重度评分：频次 × 增长趋势 × 退货关联度 × 评分影响
↓
⑨ 路由：按问题类别推送给对应团队
↓         （产品缺陷→供应链  描述不符→运营  物流→物流）
⑩ 人工确认与派单     ← ⭐ 人在环
↓
⑪ 整改追踪：记录整改动作 → 追踪后续评论变化
↓
⑫ 效果回流：整改有效性反馈，用于优化严重度模型
```

### 4.1 人在环设计

| 环节 | 是否自动 | 理由 |
|---|---|---|
| 评论聚类与打标签 | ✅ 全自动 | 只是分析，无副作用 |
| 生成问题报告 | ✅ 全自动 | 同上 |
| 严重度排序 | ✅ 全自动 | 供人参考 |
| 判定为产品缺陷并通知工厂 | ⚠️ 人工确认 | 误判会导致不必要的产线调整 |
| 触发批次召回 | ❌ 必须人工 | 高成本不可逆动作 |
| 自动修改 Listing | ❌ 必须人工 | 影响转化和合规 |

### 5.1 技术选型与理由

| 组件 | 选择 | 为什么 | 被否决的方案 |
|---|---|---|---|
| Embedding 底座 | 多语种 embedding 模型（如 BGE-M3 系列或同级） | 原生支持多语种，无需翻译对齐 | ❌ 英文单语模型 + 翻译：翻译损失 + 成本 + 延迟 |
| 微调方法 | 对比学习（InfoNCE / MultipleNegativesRanking） | 任务本质是学习"相似"的定义 | ❌ 分类微调：类别不固定，新问题会不断出现 |
| 聚类算法 | HDBSCAN（密度聚类） | 不需预设簇数、能识别噪声点、适合长尾 | ❌ K-Means：必须预设 K，且假设球形簇；评论问题分布是长尾的 |
| 降维 | UMAP（聚类前） | 高维空间密度聚类效果差 | ⚠️ 注意：降维参数会显著影响结果，要做敏感性分析 |
| 打标签 | LLM + 受控标签体系 | 需要可读的问题描述 + 可统计的标签 | ❌ 纯 LLM 自由生成：标签不一致，无法统计 |
| 严重度 | 规则 + 加权 | 可解释、可调、业务能理解 | ❌ 端到端模型：没有标签，且黑盒业务不信 |

### 5.2 ⚠️ 一个容易被忽略的设计点：受控标签体系

纯 LLM 打标签会产生这种结果：

```text
簇 1 → "充电速度慢"
簇 7 → "充电时间过长"
簇 23 → "充电效率低下"
```

三个标签，同一个问题。无法统计，无法追踪趋势。

解决方案：两层标签体系

```text
第一层：受控类别（固定，约 20–30 个）
产品缺陷 / 性能不达标 / 描述不符 / 尺寸问题 / 包装破损
物流延误 / 使用不清 / 兼容性 / 耐久性 / 安全隐患 / ...

第二层：自由描述（LLM 生成，供人阅读）
"充电功率实测仅 45W，与标称 65W 不符，多见于 iPhone 用户"
```

LLM 的任务变成：给定这个簇的代表性评论，① 从受控列表中选一个类别 ② 写一句自由描述 ③ 引用 3 条最有代表性的原文作为证据。

证据引用是必须的。业务人员不会相信一个没有原文支撑的结论。而且引用能让你评测"归因是否有据"。

## 6. ⭐ 数据方案

### 6.1 主数据源：Amazon Reviews 2023

| 项目 | 说明 |
|---|---|
| 名称 | Amazon Reviews 2023（McAuley Lab, UCSD） |
| 规模 | 约 5.7 亿条评论，覆盖 3300 万用户、4800 万商品 |
| 时间跨度 | 1996–2023 |
| 字段 | 评论文本、评分、时间、商品 ID、用户 ID、有用投票、商品元数据（类目、价格、图片） |
| 语言 | 以英文为主 |
| 获取 | Hugging Face / 官方网站 |
| 许可 | ⚠️ 使用前务必确认当前许可条款，学术研究用途通常允许 |

为什么这个数据集适合本项目：

✅ 规模足够大，可以做真正的大规模实验

✅ 有商品元数据，可以做类目分析

✅ 有时间戳，可以做趋势分析和批次模拟

✅ 有评分，可以做弱监督信号

✅ 真实数据，评论表达方式自然（合成数据做不到这一点）

### 6.2 ⚠️ 但它有三个缺陷，必须处理

| 缺陷 | 影响 | 解决方案 |
|---|---|---|
| 以英文为主 | 无法验证多语种能力 | ① 选取其中的非英文评论（存在但比例低）② 补充其他多语种电商评论数据集 ③ 用高质量翻译构造跨语言正样本对（并标注这是合成的） |
| 没有"缺陷类型"标签 | 无法直接监督训练，也无法评测 | ⭐ 见下节：人工标注金标准集 |
| 没有批次信息 | 无法验证批次关联功能 | 用时间窗口模拟"批次"，并在文档中说明这是模拟 |

### 6.3 ⭐ 训练数据构造（这是项目的技术亮点之一）

核心挑战：我们需要"哪两条评论描述同一个缺陷"的标注，但数据集没有。

解决方案：三级信号构造训练对

```text
【弱信号 1：评分 + 商品】
同一商品的两条低分评论 → 弱正样本（可能描述同一问题）
同一商品的高分 vs 低分  → 弱负样本
⚠️ 噪声大，只能作为初始信号

【弱信号 2：LLM 辅助标注】
用大模型对 N 条评论做初步的问题类型标注
同类型 → 正样本对
不同类型 → 负样本对
⚠️ 有教师模型偏差，但比弱信号 1 干净得多

【强信号 3：难负例挖掘】  ← ⭐ 技术核心
第一轮训练后，用模型自己找出：
- 向量相近但标注类型不同的样本对 → 加入难负例
- 向量相远但标注类型相同的样本对 → 加入难正例
迭代 2–3 轮
```

| 策略 | 说明 | 效果 |
|---|---|---|
| In-batch negatives | 同 batch 内其他样本作负例 | 基础，几乎免费 |
| Hard negative mining | 用当前模型检索 Top-K 相似但标签不同的样本 | ⭐ 提升最显著 |
| 跨语言难负例 | 同语言不同问题 vs 不同语言同问题 | 强化跨语言对齐 |
| 话题相同缺陷不同 | "充电快" vs "充电慢" | ⭐ 最关键，直接对抗通用模型的话题偏好 |

⚠️ 一个必须避免的坑：难负例挖掘时可能挖到"假负例"（实际是同一问题但标注错了）。要设阈值——相似度过高（如 > 0.95）的不要当负例，很可能是标注噪声。

### 6.4 ⭐⭐ 金标准评测集（红线）

训练集可以合成，测试集必须人工标注。 这是不可妥协的。

| 项目 | 规格 |
|---|---|
| 规模 | 500–800 条评论 |
| 标注内容 | ① 是否含产品问题 ② 问题类别（受控体系）③ 问题的具体描述 |
| 标注人 | 自己标 + 找 1–2 人交叉标注部分样本 |
| 一致性 | 计算 Cohen's Kappa，报告标注一致性 |
| 分层 | 按类目、语言、评论长度、评分分层采样 |
| 防污染 | ⚠️ 确保这些评论不出现在训练集中（按 review_id 排除） |

标注规范要写下来（这本身是一份可展示的产出）：

```text
标注规范示例：
1. "产品问题" 的定义：由产品本身特性导致的负面体验
- ✅ "外壳三个月就裂了" → 耐久性问题
- ❌ "快递太慢" → 物流问题，不算产品问题
- ❌ "我买错型号了" → 用户失误，不算
2. 边界情况处理：
- 描述不符（如"图片显示是白色，收到是米色"）→ 归为"描述不符"，不归为"产品缺陷"
- 一条评论含多个问题 → 多标签
3. 不确定时标记为"存疑"，不强行归类
```

|---|---|

| 使用目的 | 学习与研究 |
| 是否包含个人信息 | ⚠️ 评论含用户 ID，处理时应脱敏，不要在展示中保留 |

## 7. 模型与算法

### 7.1 完整实验设计

必须有基线。没有基线的结果毫无意义。

| 编号 | 方案 | 说明 | 预期表现 |
|---|---|---|---|
| B0 | 随机聚类 | 下界参考 | 极差 |
| B1 | 关键词规则 | 人工写 50 条规则 | 召回低、精度尚可 |
| B2 | 通用 Embedding + HDBSCAN | 主基线 | 中等 |
| B3 | 通用 Embedding + LLM 直接分类 | 不聚类，逐条分类 | 精度可以，成本高 |
| E1 | 微调 Embedding（仅弱信号）+ HDBSCAN | 第一轮微调 | 优于 B2 |
| E2 | + 难负例挖掘（1 轮） | 显著提升 |  |
| E3 | + 难负例挖掘（2 轮） | 看是否还有提升 | 边际递减 |
| E4 | E3 + LLM 打标签优化 | 完整方案 | 最佳 |

### 7.2 消融实验

| 消融项 | 变体 | 要回答的问题 |
|---|---|---|
| 难负例 | 有 / 无 | 难负例贡献了多少提升？ |
| 难负例轮数 | 1 / 2 / 3 轮 | 什么时候收敛？ |
| 训练对数量 | 5k / 20k / 50k | 数据量的边际收益曲线 |
| 底座模型 | small / base / large | 参数量的收益 |
| 降维维度 | 不降维 / 50 / 20 / 5 | UMAP 参数敏感性 |
| min_cluster_size | 5 / 10 / 20 / 50 | 聚类粒度权衡 |
| 是否跨语言训练 | 单语 / 多语 | 多语训练是否损害单语性能 |

### 7.3 严重度评分设计

聚类和打标签之后，要回答"哪个问题最该先解决"。

```text
严重度 = w1 × 频次得分
+ w2 × 增长趋势得分     ← 新出现且快速增长的最危险
+ w3 × 退货关联度       ← 该簇评论对应订单的退货率
+ w4 × 评分影响         ← 该簇平均评分
+ w5 × 安全相关         ← 涉及安全的一票否决式加权
```

为什么用规则而不用模型：

没有"严重度"的标注数据

业务需要理解和调整权重

可解释性在这里比精度更重要

### 7.4 ⚠️ 三个技术陷阱

| 陷阱 | 表现 | 解法 |
|---|---|---|
| 测试集污染 | 微调用的评论出现在测试集 | 按 review_id 严格分割，训练前检查交集 |
| 教师模型偏差 | 用 LLM 标注训练数据，模型学到的是 LLM 的偏好而非真实分布 | 金标准集必须人工标注；报告与 LLM 标注的差异 |
| 聚类不稳定 | 换个随机种子结果就变 | 多次运行取稳定簇；报告稳定性指标（如 ARI 跨种子均值） |

## 8. 工程与性能

### 8.1 这个项目的性能特点

它不是高并发在线服务，而是批量离线任务 + 轻量在线查询。

```text
离线批处理（每日 / 每周）
- 编码：40 万条评论向量化
- 聚类：全量重聚类 or 增量归簇
- 归因：只对新簇调用 LLM
→ 优化目标：吞吐量、总成本

在线查询（业务人员看板）
- 查询已有分析结果
→ 优化目标：查询延迟（但数据量小，不是瓶颈）
```

### 8.2 ⭐ 关键成本优化：把 LLM 从分类器改成解释器

朴素方案：每条评论都调 LLM 分类 → 40 万次调用，成本极高，且每天新增 300 条要持续付费。

本项目方案：先聚类，只对簇调 LLM。

```text
40 万条评论 → 聚成约 200–400 个簇
↓
每簇取 10 条代表性评论调一次 LLM
（判定类别 + 生成描述 + 选证据）
↓
LLM 调用量：40 万次 → 约 300 次
```

| 方案 | LLM 调用次数 | 相对成本 | 标签一致性 |
|---|---|---|---|
| 逐条分类 | 400,000 | 100% | 差（每条独立判断） |
| 先聚类再归因 | ~300 | <1% | 好（同簇同标签） |

⚠️ 这不只是省钱，还提升了质量——同一个簇必然得到同一个标签，标签不一致问题被结构性解决了。

### 8.3 Embedding 编码的工程优化

40 万条评论的向量化是主要计算开销：

| 优化项 | 做法 | 收益 |
|---|---|---|
| 批处理 | 合理 batch size（受显存约束） | 显著 |
| 序列长度截断 | 截断到 256 token（先分析长度分布） | 减少无效计算 |
| 长度分桶 | 相近长度放一起，减少 padding 浪费 | 中等 |
| FP16 / BF16 | 半精度推理 | 约 2x |
| ONNX / TensorRT | 导出优化（可选） | 视情况 |
| 增量编码 | 只编码新增，历史向量入库 | ⭐ 最大收益 |

要报告的数据表（数字必须你自己跑）：

| 配置 | 吞吐(条/s) | 40万条耗时 | 显存 |
|---|---|---|---|
| FP32 + batch=32 | — | — | — |
| FP16 + batch=64 | — | — | — |
| FP16 + 长度分桶 + batch=128 | — | — | — |

表格留空是故意的。抄别人的数字，一问就崩。

### 8.4 向量存储选型

| 规模 | 方案 |
|---|---|
| < 100 万 | FAISS 本地索引 / numpy |
| 100 万 – 1000 万 | FAISS + IVF/HNSW |
| > 1000 万 | 向量数据库（Milvus / Qdrant 等） |

⚠️ 不要过度设计。 团队项目在 40 万量级，FAISS 完全够。

"我评估过向量数据库，但这个数据量下 FAISS 已能满足，引入额外组件是不必要的复杂度" —— 这句话展示的是工程判断力，比堆技术栈强。

## 9. 评测体系

### 9.1 三层指标

```text
第一层：表示质量（Embedding 本身好不好）
第二层：任务效果（问题挖得准不准）
第三层：业务价值（有没有人用、有没有效果）
```

### 9.2 第一层：表示质量

| 指标 | 说明 |
|---|---|
| 检索准确率 @K | 给一条评论，检索最相似 K 条中同类问题占比 |
| 跨语言检索准确率 | 中文 query 检索英文评论 ⭐ 验证多语种对齐 |
| 类内/类间距离比 | 同类距离 vs 异类距离，越小越好 |
| 难负例区分度 | 在"话题同/缺陷异"样本对上的表现 ⭐ 核心 |

### 9.3 第二层：任务效果

| 指标 | 说明 |
|---|---|
| 问题召回率 | 金标准集中的问题有多少被发现 ⭐ 最重要 |
| 归因准确率 | 系统标签与人工标注的一致率 |
| 聚类纯度 | 每个簇内是否只含一种问题 |
| 聚类稳定性 | 不同随机种子下的 ARI ⭐ 常被忽略 |
| 噪声率 | HDBSCAN 标为噪声的比例，过高说明表示不好 |
| 证据相关性 | LLM 引用的原文是否支持结论（人工抽检） |

⭐ 为什么召回率优先于精确率：漏掉一个正在扩散的缺陷，代价是持续几周的退货和差评；误报一个问题，代价只是运营多花五分钟确认。

业务的容错方向决定指标优先级。 这个判断要写进文档——它证明你理解业务，而不是无脑追 F1。

### 9.4 第三层：业务价值

| 指标 | 说明 |
|---|---|
| 人工采纳率 | 系统提出的问题有多少被确认为真问题 |
| 提前发现天数 | 相比人工发现提前了多久 |
| 整改闭环率 | 发现的问题有多少真被整改 |
| 整改后指标变化 | 该问题的提及率、退货率变化 |

⚠️ 团队项目做不到第三层的真实数据（没有真实业务在跑）。

诚实做法：设计好采集方案，说明"这部分需实际部署后采集"。

### 9.5 ⚠️ LLM-as-Judge 必须校准

```text
① 人工标注 100 条作为参照
② 让 LLM 判官判同样 100 条
③ 计算一致率（Cohen's Kappa）
④ 分析偏差方向：偏松还是偏严？偏好某类标签吗？
⑤ 报告校准结果，而不是直接用判官分数
```

M3 §3⑧ 说过这是分水岭，90% 的人跳过。

## 10. 里程碑分解

总工期：3–4 周（每天 4–6 小时）

### Day 1–3：数据与基线

```text
□ 下载 Amazon Reviews 2023，选 1–2 个类目（建议电子配件、家居）
□ 数据探查：长度/评分/语言/时间分布
□ 清洗：去重、去广告、去无意义评论
□ 跑通基线 B2（通用 Embedding + HDBSCAN）
□ 肉眼看 20 个簇，判断质量
产出：可跑通的基线 + 数据探查报告
```

### Day 4–7：金标准集 ⭐ 最关键，不要跳过

```text
□ 设计受控标签体系（20–30 个类别）
□ 写标注规范（含边界情况和例子）
□ 分层采样 500–800 条
□ 自己标注全部
□ 找 1–2 人交叉标注其中 100 条
□ 计算 Kappa，讨论分歧，修订规范
□ 严格检查：这些 review_id 从训练集排除
产出：金标准集 + 标注规范 + 一致性报告
```

### Week 2：训练对构造与首轮微调

```text
□ 弱信号构造初始训练对（约 20k 对）
□ LLM 辅助标注一批，提升训练对质量
□ 首轮对比学习微调
□ 金标准集评测，与基线 B2 对比
□ 记录：提升多少？哪类问题改善最明显？
产出：E1 结果 + 对比表
```

### Week 3：难负例挖掘与消融

```text
□ 用 E1 模型挖掘难负例
□ 设相似度上限，过滤假负例
□ 第二轮训练 → E2
□ 再挖一轮 → E3，观察是否收敛
□ 完成消融矩阵（见 §7.2）
□ 错误分析：人工看 50 个失败案例并归类

### Week 4：归因层与系统化

□ 设计 LLM 打标签 prompt（受控标签 + 证据引用）
□ LLM-as-Judge 校准
□ 严重度评分实现
□ 批次关联分析（时间窗口模拟）

□ 工程优化：批处理、FP16、增量编码，记录性能数据

```

## 12. 常见坑

| # | 坑 | 后果 | 怎么避免 |
|---|---|---|---|
| 1 | 跳过金标准集直接训练 | 所有"提升"都是自说自话 | Day 4–7 老实标注 |
| 2 | 测试集污染 | 按 ID 严格分割，训练前 assert 无交集 |  |
| 3 | 只报结果不报基线 | B2 主基线必做 |  |
| 4 | 难负例挖到假负例 | 训练信号错误，效果反降 | 设相似度上限（如 0.95） |
| 5 | 聚类参数拍脑袋 | 结果不可复现 | 参数敏感性分析 + 稳定性报告 |
| 6 | LLM 自由生成标签 | 标签不一致，无法统计 | 受控标签 + 自由描述两层 |
| 7 | 不做证据引用 | 业务不信任结论 | 强制引用 3 条原文 |
| 8 | 忽略噪声点 | 漏掉罕见但严重的问题 | 噪声点单独做安全扫描 |
| 9 | 用 LDA | 技术选型过时 | 见 §3.1 |
| 10 | 编造业务收益 | 一问就崩 | 明确区分实测/测算 |
