## 1. 给接手智能体的最短上下文

**产品**：面向中小跨境卖家的选品尽调 Agent。用户带着候选品类或竞品来，系统先判断能不能做，再告诉如果做从哪里切。

**目标用户**：1–3 人的跨境小团队 / 中小卖家的选品负责人。长期目标是 SaaS，当前只做 MVP。

**必读顺序**：

1. 本文件
2. [00-方向决策.md](00-方向决策.md)：为什么做、市场空位、产品边界
3. [02-v0-技术方案.md](02-v0-技术方案.md)：数据、模块、规则、排期（**冲突时以 02 为准**）
4. [01-MVP-v0.md](01-MVP-v0.md)：v0 范围与不做清单
5. [research/P01](research/P01-多源选品评分与蓝海挖掘.md) 与 [research/P02](research/P02-评论缺陷挖掘与产品改良引擎.md)：原始调研

**四条硬约束**：

- 只用公开数据，不爬平台，不采个人信息。
- 不预测销量；评论是代理指标，必须标注。
- 所有结论必须能回溯到数据、公式或原文证据；假设值单独列出。
- 原始调研里的 76% / 40% 来自虚构案例，不得对外引用。

## 2. P01 / P02 分工

**P01 负责否决**：用硬规则和确定性算式，先判断这个品「能不能做、值不值得做」——合规不过、算不过账、竞争没位置，就出局。

**P02 负责破局**：只对活下来的品，从评论里挖出「可修复、持续、有原文证据」的切入机会，回答「如果做，从哪切」。

逻辑顺序是 **P01 → P02 → 备忘录整合**。开发验证可以 P02 先行，因为它决定产品是否成立；文档和决策顺序不变。

## 4. 已拍板，不要重开

除非用户明确改变，以下不再重新论证：

1. **方向**：选品尽调 Agent，不是又一个选品数据面板。
2. **定位**：付费点是「你的数字 + 硬否决 + 原文证据 + 放弃条件」。
3. **数据**：Amazon Reviews 2023 · Appliances，抽样 100 万；3C 作为第二实验。
4. **逻辑顺序**：P01 否决 → P02 破局 → 备忘录。
5. **引擎**：bge-small + KMeans 主链路，HDBSCAN 只做对照；微调不做。
6. **归因**：Opus 5.5，簇级调用，强制证据。
7. **利润**：输出采购价上限与到岸成本两个数，不用模型算钱。
8. **竞争**：近 12 个月窗口，不用生命周期累计。
9. **开发期不做兼容分支**：旧数据可直接丢弃，用新数据测试。

## 8. 工作约定

- 环境：Python 3.11 + `uv`；所有外部调用可缓存。
- 确定性模块（利润、费率、规则）必须有单测；不引入模型。
- LLM 只做簇级归因和解释，不逐条分类。
- 任何报告都要能回答「这个数字从哪来」；回答不了就不写。
- 不把「评论」写成「销量」，不把「代理」写成「事实」。
- 不为了跑通而造假数据；缺什么就标什么，或让用户输入。
