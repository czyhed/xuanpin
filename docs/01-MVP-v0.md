# MVP v0：用公开数据跑通「一个类目 → 决策备忘录」

**P01 负责否决**：用硬规则和确定性算式，先判断这个品「能不能做、值不值得做」——合规不过、算不过账、竞争没位置，就出局。

**P02 负责破局**：只对活下来的品，从评论里挖出「可修复、持续、有原文证据」的切入机会，回答「如果做，从哪切」。

目标：先做出来看。不接真实店铺、不接实时采集、不做账号和付费，只用公开数据把端到端链路跑通，验证这个产品到底有没有用。

> 本文是范围文档；数据选型、公式修正、技术实现和排期以 [02-v0-技术方案.md](02-v0-技术方案.md) 为准，两者冲突时以 02 为准。

## 0. v0 要证明的三件事

1. **能从评论里挖出可行动的切入角度**：某个类目的 Top 缺陷是什么、占比多少、持续多久、改起来贵不贵，并引用原文。
2. **能刻画竞争结构**：集中度、新品存活率、价格带，而不是「竞品数量」。
3. **能给出明确结论与否决项**：可做 / 有条件可做 / 不建议，每个结论都能回溯到数据或计算过程。

只要这三件事成立，产品就成立；UI、账号、实时数据都是后面的事。

## 1. v0 明确不做

- 不预测销量（只用评论增长、排名等代理信号，并标注）
- 不做实时监控（P41 留到 V1）
- 不做多语言（v0 只做英文）
- 不做自动上架、自动改价
- 不爬平台、不绕反爬、不采集个人信息
- 不做登录、计费、多租户

## 2. 四个关键设计决策

### 2.1 反向利润测算：不猜成本，算「最高可接受采购成本」

没有真实采购价，直接算净利率一定是编的。改成反推，并同时输出两个数：

- **采购价上限**：这个售价下，供应商 FOB 报价最多能到多少。
- **到岸成本**：采购价上限加上头程、关税、仓储后的实际到岸金额。

卖家拿供应商的 FOB 报价或到岸报价分别对，不会拿错口径。完整公式、美国 FOB 与欧盟 CIF 的税基差异见 [02-v0-技术方案.md](02-v0-技术方案.md) §4.3。

所有参数标注来源：用户输入 / 公开费率 / 假设。假设值单独列，允许用户改。

### 2.2 硬性否决不打分

合规、毛利、体积重、侵权、认证触发即出局，不管销量多好。理由见 P01 §4.1。

### 2.3 只报「三高一低」的缺陷

一个缺陷要成为切入机会，必须同时满足：

- 提及频次高
- 时间上持续（不是一批货的偶发问题）
- 改造成本低（软件、说明、包装可以解决；换模具不行）
- 有原文证据

四条不满足的缺陷只进附录，不进结论。

### 2.4 结论必须能被推翻

备忘录里必须写「放弃条件」和「待确认清单」。说不出什么情况下该放弃的报告，等于没有结论。

## 3. 数据

| 数据 | 用途 | 来源 | v0 风险 |
|---|---|---|---|
| Amazon Reviews 2023（评论 + 商品元数据） | 缺陷挖掘、竞争结构、趋势 | McAuley Lab，HuggingFace | 类目文件大、国内下载慢，见 §7 |
| 亚马逊费率表 | 佣金、FBA 配送费 | 卖家后台公开页面，人工整理成 YAML | 需标注抓取日期，费率会变 |
| 合规规则 | 硬性否决 | 公开法规与平台政策，人工整理成 YAML | 只给「需核查 + 依据」，不给法律意见 |
| Google Trends | 需求趋势（可选） | 公开接口 | 不稳定，不作为阻塞项 |
| 采购成本 | 反向利润测算 | 无，改为「最高可接受成本」 | 已用反向测算规避 |

**类目选择**：v0 用 Amazon Reviews 2023 的 Appliances（评论 210 万，商品 9.4 万），随机抽 100 万条。2023 版没有 50–200 万评论的 3C 类目——Cell_Phones 有 2080 万条，超出 v0 的迭代节奏。Appliances 的缺陷（漏水、噪音、寿命、安装）同样能验证缺陷引擎；3C 作为第二实验，不阻塞 v0。

## 4. 输入与输出

**输入**

- 必填：类目 / 子类目，或一组竞品 ASIN
- 选填：目标市场、目标售价、目标毛利率、物流方式

**输出：一页备忘录**

```text
结论：有条件可做
━━━━━━━━━━━━━━━━━━━━━━
① 否决项（0 项触发 / 1 项需确认）
   需确认：锂电池运输需 UN38.3 报告，依据 [链接]
② 竞争结构
   评论集中度 0.61（偏集中）｜Top10 份额 43%
   近 6 个月新品存活率 27%（低）
   价格带 12–29 美元，主流 18–22
③ 利润测算
   目标售价 19.99｜佣金 15%｜广告 12%｜退货 6%
   采购价上限：按售价反推（FOB）
   到岸预算上限：$6.4
   ⚠️ 广告占比与退货率为假设值，可按你的实际数据改
④ 缺陷机会（按可行性排序）
   1. 充电口松动 / 接触不良 —— 提及 18%，持续 9 个月
      改造成本：低（结构件+说明）
      证据：「用了三周，插头就开始晃」等 3 条
   2. 说明书不清 —— 提及 11%，持续 14 个月
⑤ 放弃条件
   打样 FOB 报价 > 采购价上限，或到岸报价 > $6.4；上架 30 天评论增速 < 5 条/周
⑥ 待确认
   - 供应商能否提供 UN38.3
   - 结构件改模是否需要新开模
```

数字只是格式示例，真实输出必须来自数据。

## 5. 模块划分

```text
src/selection/
  ingest/       数据下载、类目过滤、清洗、语言识别
  features/     商品级特征：价格、评论数、评分轨迹、上架时间
  competition/  集中度、Top10 份额、新品存活率、价格离散度
  defects/      Embedding、聚类、受控标签、LLM 归因、证据引用
  economics/    费率表、反向利润测算
  compliance/   规则库、硬性筛除
  brief/        结论逻辑、备忘录渲染
  eval/         回测、指标、错误分析
  interfaces/   CLI（先）→ Streamlit（后）→ API（SaaS 时）
```

原则：core 不依赖 UI；每个模块输入输出有类型；数据下载和模型推理可缓存，保证反复跑不重复花钱。

## 6. 里程碑（约 2 周，每天 4–6 小时）

**M1｜数据与基线（2–3 天）**
- 下载一个类目，清洗、去重、语言过滤
- 商品级特征表 + 时间切分（T1 特征期 / T2 表现期）
- 基线：按评论数排序
- 产出：数据探查报告 + 基线指标

**M2｜缺陷引擎（3–4 天）**
- 通用 Embedding + 聚类基线
- 受控标签体系（20–30 类）+ LLM 归因 + 证据引用
- 人工标注 200 条金标准，算召回/准确率
- 产出：缺陷分布 + 评测结果

**M3｜结构、利润与规则（3 天）**
- 集中度、新品存活率、价格带
- 费率表 + 反向利润测算
- 合规规则库（先覆盖 1 个类目）
- 产出：结构化特征 + 否决逻辑

**M4｜备忘录与回测（3 天）**
- 结论逻辑 + Markdown/HTML 备忘录
- CLI 跑通，再做 Streamlit 单页
- 回测：T1 → T2，对比「按评论数排序」基线
- 产出：可演示的端到端 demo + 一页实验结论

## 7. 已知风险与预案

| 风险 | 预案 |
|---|---|
| 数据集下载慢或打不开 | 用 HuggingFace 镜像；先取一个中等类目；支持按行数截断 |
| 磁盘只有约 30GB | 只保留需要的列；评论截断到 256 token；中间结果用 Parquet |
| Embedding 模型太大 | v0 用轻量多语种模型，接口可替换；BGE-M3 留到效果验证后 |
| LLM 调用成本 | 只对簇调用；结果落盘缓存；同一簇不重复调 |
| 没有真实卖家验证 | 先做公开数据回测 + 自己跑 3 个类目；卖家访谈放到 demo 之后 |
| 结论被质疑是编的 | 所有数字带来源或计算过程；假设值单独列出 |

## 8. 成功标准

v0 算成功，只要满足：

1. 端到端能在 10 分钟内跑完一个类目，产出一页备忘录。
2. 缺陷召回率（200 条人工标注）≥ 70%，且每条结论有原文证据。
3. 回测中，机会排序优于「按评论数排序」基线。
4. 自己看 3 个类目的备忘录，能说出「这个结论我会用 / 不会用，因为……」。

第 4 条是产品判断，比任何指标都重要。
